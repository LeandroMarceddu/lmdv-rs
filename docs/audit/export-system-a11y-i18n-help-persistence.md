**Scope:** `docs/BEHAVIOR_SPEC.md` §2.6 X (16 rows), §2.11 S (27), §2.14 H (13), §2.15 A (15), §2.16 I (11), §2.17 P (20) — 102 rows.
**Checkout:** audit run 2026-11-20 against the working tree (`docs/STATUS.md` last updated 2026-11-18, Rune `cca5df6`).

## Method

- Read every row's behavior, priority and acceptance criterion, then looked for evidence that the behavior exists in this checkout.
- Evidence accepted: a named test (file + test name), a scene key, a script under `tests/scripts/`, a fixture, or a note in `docs/STATUS.md` / `docs/OPEN_ITEMS.md` / `docs/FEATURE_PARITY.md`. Source was opened to confirm or qualify a claim (whether a clause has an implementation, whether a string is localized, whether a wiring exists).
- `done` requires evidence that exercises the row's behavior; a neighboring test does not count. Where a row's mechanism is implemented but has no test/scene/manual note, it is `partial` with the gap named — code alone was not accepted as `done`.
- `substitute` means the behavior is delivered by another mechanism or is an accepted gap, cited to `docs/FEATURE_PARITY.md` §4, an ADR, an OI row, or the spec's own Linux table (§3.19).
- `partial` means the behavior is largely present but a named clause is missing, contradicted, or untested; the gap is named in the cell.
- `missing` means no implementation (or no app wiring) was found. `n/a` is platform-specific and says why.
- P rows are audited against the **native XDG store** (ADR-010), not the WebView `localStorage`/`sessionStorage` keys the baseline used. A row whose only difference is the storage medium is `substitute`, not `missing`, when the behavior has tests.
- Tests were read by name, not executed. No workspace suite was run (AGENTS §4); no code, spec, checklist, `OPEN_ITEMS`, `STATUS` or `FEATURE_PARITY` file was changed. This file is the only change.
- Table order follows the spec's section order: X, S, H, A, I, P.
